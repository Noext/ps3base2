The SPURS abort at ~86-94 s was replayed four ways on the same binary:

```
default : SPURS is aborted = 1, exit -2147418100
shadow  : SPURS is aborted = 1, exit -2147418100     (SPU_SHADOW=1)
noaot   : SPURS is aborted = 0, exit (none)           (SPU_NO_AOT=1)
strict  : SPURS is aborted = 0, exit (none)           (SPU_STRICT=1)
```

Two conclusions, both from that table:

1. SHADOW does NOT cure it, so the interpreter reading the same SPU program hits the
   same abort. The SPU program itself, and the runtime's view of it, are consistent.
2. NO_AOT DOES cure it. The difference between the two paths is therefore in the
   AOT-compiled SPU blocks: a block compiles that does not do what the interpreter
   does for the same instructions.

So the leaf is in the SPU compiler, not in channel semantics. T1: your 'last 200
blocks executed by SPU 0' dump plus the block hash at the abort is now the decisive
artifact -- take it from the AOT run, and compare the offending block against the
same block under SPU_SHADOW. T3: your channel audit is still wanted, but rank it
after any channel that appears in that block.
